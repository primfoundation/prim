## A measurable definition of 95%

Use the following **proposed release-readiness rubric**, fixed before the next
assessment. It measures accepted outcomes, not hours spent, test counts, PR
counts or permanent completion of the Foundation mission. Each goal has five
explicit outcomes; an outcome earns its full weight only when its stated scope
is supported by retained evidence. Partial work is described in the canonical
requirements and earns no invented fractional acceptance credit.

| Goal | Weight | Five outcomes, in order; each receives one fifth of the goal's weight |
| --- | ---: | --- |
| G1 Standards | 20 | Small common contract; complete Research exchange; six diverse reference cases; authenticated portable distribution; reproducible SDK/tooling and outside author acceptance |
| G2 Public Hub | 15 | Canonical human/JSON/MCP discovery with ownership/moderation boundaries; production compatibility and rollback; real supported MCP-client connection; consented popularity collection; accessible self-service local authoring |
| G3 Primboard | 15 | Encrypted atomic/concurrent store; capture-to-conversion-to-complete-export workflow; signed installed release with preserved identity; backup/key-recovery and permission behavior; representative performance and device-failure acceptance |
| G4 Browsers | 10 | Real Apple login; container/session isolation; production cookie/route compatibility; monitored rollback and recovery; documented installed usage and accountable ownership |
| G5 Desktop | 15 | Verified source and reconciled integrations; generic attachment-preserving file editing; in-app authority/FDA and distinct XPC proof; signed upgrade/file-association acceptance; accessible ordinary filing and retrieval |
| G6 Migration | 10 | All 17 incubators classified; ORF/Workbook consumers preserved; public semantic migrations with loss reports; private/license/tooling dispositions; administrative successor renames and eligible archives |
| G7 Durability | 15 | Accepted governance/legal roles; enforced scoped agency and reviewed security response; approved costs and support/maintenance; replacement-maintainer restore/deploy/exit drill; consented outside adoption and maintained education/diagnostics |

The arithmetic is `sum(weight of accepted outcomes)`, out of 100. Every outcome
assessment must cite the relevant requirement IDs, exact source/release,
environment, test scope, reviewer where required, limitations and evidence.
Keep the dated calculation as an evidence snapshot, not a second status system.
D95-02 must audit the eleven in-review rows for their actual missing reviews
and produce the first scored baseline before reporting a new current percentage.
No outcome is credited merely because this plan exists.

**Claiming 95% requires both at least 95 accepted points and every critical gate
below.** An open critical gate vetoes the claim even if a numerical sum is high.
The current percentage is therefore unscored, not asserted to be 75% or 95%.

The only candidate final-five-percent deferrals under this rubric are:

- **G2 outcome 4, three points:** activating optional consented popularity
  collection. Identity, directory moderation, privacy and honest empty states
  must already work; telemetry remains off until its own gates pass.
- **G6 outcome 5, two points:** administrative repository renames/archives after
  successors, compatibility, ownership and reversibility are proved. Keeping a
  clearly labeled historical repository open does not break the user journey.

These are candidates, not approved scope removals. Any deferral needs the exact
open requirement/obligation, reason, accepted risk, named owner, next action and
review date. Its requirement remains open. No missing Desktop, reference case,
attachment preservation, independent review, security, real-user or operating
gate can be placed in the final 5%. Changing weights or scope requires a visible
decision and a recalculated baseline; it cannot be used to reach the number.

## Critical acceptance gates

1. A new user can install, find/create a Prim, add evidence, edit, search, recover
   and export it without GitHub, a terminal or schema terminology.
2. A complete artifact moves between two installed implementations and an offline
   environment without losing original bytes, unknown fields, identity or history.
   A generated view names its authoritative source revision.
3. Research completes a real publish/discover/create/challenge/revise/reopen path;
   all six reference cases expose and resolve the shared model's weaknesses.
4. Publisher/agent identity and authorization are enforced. Hashes, described
   capabilities, context membership, structural validity and truth remain separate.
5. Real signed native candidates preserve established identities and stores.
   Wrong-app launch, key loss, concurrent edits, corrupt data and permission denial
   have safe, usable outcomes. No unmitigated critical data-loss/privacy issue remains.
6. Hub and Browsers production releases have actual external-client/account proof,
   quotas, accountable operators and observed rollback/recovery. A preview is not
   silently relabeled production.
7. Every repository and old consumer has a preserved migration or explicit
   private/tooling/history disposition. Unknown source rights are not papered over.
8. Independent technical/security review, representative user tasks and an outside
   maintainer's recovery/continuity exercise pass for the declared release scope.

governance and operator ownership start early because other work depends on their
entry artifacts; final reviews happen against release candidates. `entry_from`
in `plan.json` identifies prerequisite artifacts, not a claim that every
requirement in the preceding package is already complete. Canonical requirement
dependencies still control when completion can be recorded.

Do not promise a calendar date before the source/build and independent-acceptance
gates are understood. At the end of wave 0, estimate each bounded implementation
increment and separate active engineering time from account/consent/review wait.
Reforecast after each product acceptance, using observed results. The number of
documents or waves finished is never converted into project percentage.
